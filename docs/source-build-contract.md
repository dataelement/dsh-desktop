# 源码与构建产物规范

## 1. 唯一维护入口

本仓库维护的每项能力必须有明确的权威输入。业务修改落在该输入及必要的构建脚本、测试中；机器可生成的副本不作为第二份代码提交和评审。

| 文件性质 | Git 策略 |
| --- | --- |
| 自有维护代码、手工资源、模板原始输入、生成器 | 跟踪，作为构建输入 |
| 从上述输入生成的 bundle、tgz、预览图、产物哈希清单 | 构建时生成，输出到明确的忽略目录，通过 CI artifact / release 分发 |
| 未在本仓库维护其源码的第三方固定分发包 | 可作为 vendored 依赖输入保留；记录来源、版本和完整性，不私自改包 |
| 依赖锁文件 | 跟踪；用于锁定外部依赖，不能为避免差异而删除或忽略 |

文件角色按来源判断：`lib/client.js` 可能是实际维护代码，`build/` 也可能包含手工输入；不能笼统忽略 `lib/`、`build/` 或所有 `.tgz`。生成的 manifest/hash 与依赖锁文件也不是同一种文件。

## 2. 生成必须进入实际构建链路

- 新增自有包或生成步骤时，同步接入实际使用它的 dev、build、test、package/release 路径。可以复用同一个准备步骤；不得要求开发者记得先手工打包。
- 普通源码改动不应要求重新提交自有 tgz、手抄产物哈希，或只为该 tgz 的内容变化更新依赖锁文件。出现这种 diff，应检查是否把生成物错误地当成安装输入。
- 生成结果写入独立输出/staging 目录，不覆盖维护源码，不回写受 Git 跟踪的模板或清单。`npm run build` 不应让工作区产生受跟踪文件差异。
- 生成必须先于消费；缺少生成输入或生成失败时立即失败，不能悄悄使用上次留下的包。打包必须包含本次构建结果，而非开发机缓存或旧 `node_modules` 副本。
- 测试应消费本次生成的实际分发内容；只验证维护目录不能证明安装包正确。检查生成包的入口、exports、必要资源和运行时加载，不止检查文件存在。
- 构建依赖显式声明并锁定，不能依赖偶然安装的传递依赖、个人机器工具或未固定的网络资源。原生生成步骤仍遵循目标平台要求。
- 输入相同且工具环境固定时，产物内容应可复现；归档时间戳、路径和文件顺序应规范化。平台渲染造成的不可避免差异需明确，不能以此掩盖代码或资源缺失。

## 3. 安装顺序不得形成循环

若 `package.json` 的 `file:...tgz` 指向已移出 Git 的生成包，首次 `npm ci` 会在 build 之前失败。不得只改 `.gitignore` 或在 postinstall 中补打包来掩盖此依赖循环。

迁移时根据实际加载器选择：

- 自有包以本地源码包参与依赖安装，构建阶段准备发布目录，并验证最终分发包含完整文件而非仅开发机可用的链接；或
- 将构建依赖的安装与自有产物的生成、组装分开，提供统一入口，让干净环境能先获取生成工具，再生成并装配产物。

不强制引入 workspace 或更换包管理器。必须给出没有旧产物时也能成功的安装与构建顺序，并同步调整 CI、测试和文档。

## 4. 存量迁移与预防检查

- 禁止新增源码与自有生成包双重跟踪。现有链路采用独立迁移变更，不在小型业务修复中直接删除仍被安装依赖引用的文件。
- 迁移必须一起处理依赖引用、构建入口、输出目录、Git 跟踪、测试、完整性校验和发布组装；依赖仍指向旧包时不能宣称迁移完成。
- CI 的目标检查：从干净 checkout、无旧输出的环境完成依赖安装及生成；验证本次产物；确认构建没有改写受跟踪文件。
- 对明确的自有产物输出目录增加“不得被 Git 跟踪”检查。`.gitignore` 不会阻止已经被跟踪的文件继续提交；不能仅靠它作为门禁。
- 产物输出目录的门禁不能误伤固定第三方分发输入。例外必须能解释其来源和不可由仓库输入生成的原因，不能以“安装方便”保留自有产物双份维护。

## 5. PR #369 对应的现状与目标

本次检查发现：#369 同时修改 `packages/ppt-runtime/{core,adapter}/lib/client.js`、`packages/ppt-bundles/*.tgz`、`artifacts.json` 和锁文件中的 integrity。维护代码与由它生成的包被重复跟踪。

当前已有 `scripts/build-ppt-runtime.mjs` 和 `ppt:build`，但普通 build 和 release workflow 未调用该生成命令；`package.json` 直接引用已提交的 PPT tgz。生成器还会写入维护目录下的预览图和清单，因此不能不经调整就直接接到普通 build。

目标是：维护代码与模板原始输入 → 构建生成预览/清单及插件分发内容 → 应用打包。开发者提交代码、输入和脚本，CI 保存和分发产物；完整性值由生成流程计算。

本文新增开发与评审约束，尚未迁移现有 PPT 构建流程或启用上述 CI 门禁。PR #369 的业务修复与构建链路迁移应分别说明验证结果。
