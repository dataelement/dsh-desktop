# PR 提交与评审

本规范用于 DSH Desktop 仓库。代码、加载、补丁和构建的详细要求分别由根 `AGENTS.md`、目录规则、[Patch 与 Plugin 规范](patch-plugin-contract.md)和[源码与构建产物规范](source-build-contract.md)维护，这里只规定提交范围和证据组织。

## 1. 一个 PR 解决一个可评审的问题

- 描述用户遇到的具体触发条件、修改后的行为和影响范围。不要将宿主修改、独立工作台适配、Awesome 收录、统计采集和正式发布混成一次交付；跨仓库依赖用 PR 链接说明先后关系。
- 从目标分支创建隔离分支，保留已有 WIP。提交前检查暂存差异和整个 PR 的 changed files；不要把本地其他任务、生成目录、缓存或诊断材料带入提交。
- 小修复不捆绑无关重构。删除生成物时必须同时修复首次安装、构建、打包和验证链路，不能只增加 `.gitignore`。
- 不修改与本任务无关的插件、条目或第三方分发包；源码改动和第三方包升级分清来源，不能为了让测试通过修改固定第三方 tgz。

## 2. 按职责审查，不把宿主规则扩散成收录门槛

| 变更归属 | PR 应提供的证据 |
| --- | --- |
| Desktop 宿主 | 受影响进程与公开接口、失败恢复方式、相关行为回归及实际平台验收 |
| 独立插件 / 工作台 | 自身源码构建、最终安装包内容及所声明宿主版本上的加载验证；在该项目提交 |
| Awesome 目录 | 投稿元数据、仓库/安装来源身份、实际产物的协议校验及条目范围；遵循目录自身规则 |

`dist/`、`lib/` 或 `dsh/engines.mjs` 这样的路径不是所有工作台的通用接口。应区分文件是否为本项目生成物，以及最终包是否包含 manifest、exports、bundle patch 等声明引用的内容；不能要求作者仅为收录而将编译结果提交到 Git。

宿主开发规范（如 IPC、slot 生命周期、主题 token）由对应宿主/插件仓库维护。目录可以核验明确的安装协议，但不复制整套 Desktop 工程规范，也不把静态格式检查宣传成完整运行验收。

## 3. 来源与安装产物必须对应

- **npm**：验证实际下载的固定版本包、仓库归属和完整性。源码默认分支不含构建输出，不构成拒绝一个完整发布包的理由。
- **Release Asset**：验证选中的同仓库固定资源及校验值；附件如何选择由目录协议定义，不能猜测某个通用文件名。
- **源码构建**：写清固定 commit、依赖锁定、构建与打包入口、产物保存和交付位置；在隔离、无发布凭据的环境运行作者构建代码，再校验最终包。未实现构建时必须写明限制，不能把“检查源码入口存在”称为“完成源码打包”。
- 验证以选中的安装产物为准；开发分支状态不能无说明地替代发布版本状态。安装包可引用不同于源码的生成路径，但最终声明的入口及必要资源必须完整。
- 构建删除/忽略输出后，从干净 checkout 完成验证。源码测试通过不替代实际 tarball、应用资源目录或安装器检查；Git 忽略与分发包包含是两个独立规则。

以上是新实现和 PR 评审要求，不表示 Desktop 或外部目录已支持全部来源路径。跨仓库协议变更必须说明当前能力、目标能力及未完成的消费者接入。

## 4. PR 描述与验证记录

使用仓库 PR 模板，按实际影响填写，简单改动不必写无关段落：

1. **问题与结果**：具体触发条件、修复后的行为。
2. **范围与依赖**：影响模块、宿主/包版本或来源、关联 PR；协议变化说明消费者迁移方式。
3. **验证**：实际执行的命令、平台、产物或 commit、结果。涉及构建产物时说明干净安装和最终包检查；涉及运行行为时说明实际应用流程。
4. **未完成项与恢复**：未验证的平台/路径，以及与改动相关的回滚或数据恢复方式。

纯文档修改只检查差异、链接和命令真实性，不要求重装依赖或启动应用。代码改动按根规范执行相关回归、typecheck、build 和完整测试；不存在的脚本不能填为通过。

明确区分本地通过、远端 CI 通过、PR 已合并、包已发布、用户应用已安装并加载。未执行的验收标注未验证，不填勾。规范中要求的检查不等于已配置自动门禁；目前没有覆盖所有上述约束的自动 PR 检查。
